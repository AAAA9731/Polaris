# Polaris Core 宪章

Core（`PolarisCore.dll`）是给《Alice in Cradle》BepInEx 模组作者铺的一道台阶：把每个模组都要重复写、又容易写错的那一层做好一次。它**不是**一个什么都管的框架。这份文件规定什么能进、什么不能进。

## Core 是什么

| 领域 | 入口 | 解决的重复劳动 |
| --- | --- | --- |
| 设置 | `[PolarisSettingGroup]` / `[PolarisSetting]` / `[PolarisButton]` | 声明字段就有持久化、设置页、搜索、条件显示 |
| 存档 | `PolarisAPI` 的 Save | 模组自己的存档分区，不污染原版存档 |
| 事件 | `PolarisAPI.Events` / `[PolarisSubscribe]` | 订阅游戏生命周期事件，不用自己打补丁 |
| 本地化 | `PolarisAPI.Localization` | 文案键、文案文件、多语言 |
| 菜单 | `MainMenu` / `GameMenu` | 标题菜单按钮、暂停菜单分类 |
| 资源 | `Res` | 图片、音频、PXLS 的加载与缓存 |
| 输入与提示 | `Game.Input` / `Game.UI` | 可改键的热键、给玩家一行提示（`Notify`/`Warn`）、需要玩家做决定时的确认框（`Confirm`） |
| 基础设施 | `PolarisMod`、`Patching`、`Errors`、`Paths` | 安全打补丁、异常不拖垮游戏、目录约定 |
| 游戏门面 | `PolarisAPI.Game` | 对原版对象的安全只读访问 |

## 准入规则

新增任何东西之前，过这几关：

1. **冲突测试**：两个模组各自做这件事会不会互相打架？会（例如都改标题按钮、都加暂停菜单分类）就该由 Core 统一管；不会就别收。
2. **坑测试**：这件事有没有每个作者都会踩的坑（例如热键在输入框里打字时误触发、异常从按钮回调里漏出去）？有，值得收。
3. **三次规则**：同样的代码要在三个以上模组里出现才抽进来。当前只有 Noels 一个使用者，所以现阶段看的是"别的模组很可能也要"。
4. **能不能放文档或模板**：能靠 `templates/` 里的示例或文档讲清楚的，不进 dll。

### 语法糖

语法糖欢迎：重载、默认参数、特性声明式写法，只要它**只是组合 Core 自己已有的 API**，随便加，不需要理由。
包装游戏类型的糖统一放在 `PolarisAPI.Game` 门面里，并且带 try/catch，游戏没就绪时返回安全的默认值。

### 带补丁的功能

每个事件、每个游戏封装背后都是一个 Harmony 补丁，会随游戏版本失效，这是 Core 唯一的维护风险。所以：

- 新增"对游戏的补丁"，应当有至少一个真实使用者。
- 例外：**生命周期事件**（标题就绪、菜单开关、场景切换、玩家出现等）作为一类整体接受，不需要逐个等使用者。
- 每个补丁独立成类，坏一个只丢它自己（`PatchingAPI.ApplyAll` 逐类应用），不连累其它功能。

## 明确不做

这些是上游那一系列膨胀的原因，Core 不收，留在各模组自己里：

- 战斗、魔法、地图、物品栏、AI 等**原版领域**的封装
- 新的文件格式或资源类型（视频已经砍掉）
- 联机、同步、网络传输
- 任何"一个模组独有、别的模组用不上"的东西

想加这类东西，先问：能不能是一个**依赖 Core 的独立模组**？绝大多数情况答案是可以。

## API 稳定性

Core 目前是 **0.x**：

- 不承诺向后兼容。破坏性改动会写进发布说明，使用者在升级 Core 时需要跟着改。
- 等第二个真实使用者出现、API 形状稳定后，再升到 1.0 并开始承诺兼容。
- `internal` 的东西随时可改，只有 public 的才算 API。

## 谁来管什么

| | Core（`PolarisCore.dll`） | ModManager（`ModManager.dll`） |
| --- | --- | --- |
| 性质 | 库，被别的模组引用 | 产品，玩家直接用 |
| 内容 | 上表的各领域 | 诊断、崩溃报告、模组管理页、自我更新 |
| 依赖方向 | 不依赖 ModManager | 依赖 Core |

Core 只通过 `IErrorBackend` 这类接口和 ModManager 打交道，从不引用它。
